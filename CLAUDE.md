# PatternChess

Chess training app using the woodpecker method. **Vite + React + TypeScript** SPA targeting Chrome.

## Stack
- Vite 5 + React 18 + TypeScript (strict)
- React Router v6
- Tailwind CSS — palette in `tailwind.config.ts`, dark charcoal/brown
- TanStack Query (server state) + Zustand (training/review state machines)
- Backend on **Cloudflare Pages Functions**, same origin as the SPA (2026-11-22, PR #47 `feat/cloudflare-backend`; replaced Supabase — **production runs on this backend** since the cutover in `docs/cutover-cloudflare.md`, 2026-11-22; only the "after two quiet weeks" Supabase shutdown is left):
  - `better-auth` 1.7 at `/api/auth/*` (Google + Lichess via `genericOAuth`; sessions + rate limits in KV `AUTH_KV`; first-party httpOnly cookie)
  - D1 `patternchess-app` (bound `DB`) for all app data + better-auth tables; Kysely + `kysely-d1` only inside better-auth, plain D1 statements everywhere else
  - RPC API `POST /api/rpc/:name` (registry in `functions/_shared/rpc/`), client `rpc()` in `src/lib/api.ts`
  - KV `CONTENT` (supporter articles + course days), D1 `patternchess-book` (`BOOK`, opening book), `stripe` SDK in Functions
- `chess.js` for chess logic / PGN parsing
- `chessground` (Lichess JS) wrapped in a small React component
- Stockfish WASM v18 (nmrugg lite MT primary, lite ST fallback) in a Web Worker

## Setup

1. `npm install`
2. `.dev.vars` (gitignored, read by `wrangler pages dev`): `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL=http://localhost:8788`, `AUTH_TEST_MODE=1` (email/password test sign-in), optional `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` (the Google provider is omitted without them; Lichess needs nothing — public PKCE client `patternchess`), `STRIPE_*` test values. `.env.local` holds `CLOUDFLARE_ACCOUNT_ID` for wrangler (plus `VITE_SUPABASE_URL`/`SUPABASE_SERVICE_KEY`, used only by `npm run migrate:export`, kept until the Supabase project is paused).
3. `scripts/dev-api.sh` (keep it running) — applies pending D1 migrations to the local store and runs `wrangler pages dev` on `:8788` with `DB`, `AUTH_KV` and `CONTENT` persisted under `.wrangler/state` (see `d1/README.md`; the local DB holds a copy of production data, reload it with `npm run migrate:import -- --local --fresh`).
4. `npm run dev` — Vite serves at `http://localhost:5173` with the COEP/COOP headers needed for SharedArrayBuffer + Stockfish multi-threading, and proxies `/api/auth`, `/api/rpc`, `/api/stripe`, `/api/articles` to `:8788` (`/api/book` is the in-process `devBookProxy`). Sign in locally with `POST /api/auth/sign-up/email {email,password,name}` (test mode) or `scripts/smoke-auth.sh`. Dev builds show a **Local test sign-in** form on `/login` (`DevSignInForm`, `import.meta.env.DEV` only): sign in, or "Create account" (an `@lichess.invalid` address behaves like a Lichess sign-in with no email).
5. Optional: `scripts/dev-notifier.sh` runs the email Worker on `:8791` against the same local D1 (`STATE=` like dev-api.sh) with `DEV_MAILBOX=1`: emails are kept in memory, never sent, and http://localhost:8791/dev/mailbox lists them (links point at `:5173`/`:8791`) and runs the hourly job for one account. Content: `npm run courses:sync -- --local` and `npm run articles:sync -- --local --drafts` (drafts go to the gitignored `src/generated/articles.local.json`, which only dev builds read). Supporter checkout: `stripe listen --all-snapshot --forward-to localhost:8788/api/stripe/webhook`.

## Conventions

- **Routing**: SPA with React Router v6. `/login` is public; everything else is gated by `<RequireAuth>` inside the `<AppShell>` layout.
- **Auth** (better-auth, 2026-11-22): server config in `functions/_shared/auth.ts` (`getAuth(env)`), mounted by `functions/api/auth/[[path]].ts`. D1 via Kysely `D1Dialect` with `validateSchema: false` (`d1/migrations/0002_auth.sql` owns `user`/`session`/`account`/`verification`/`rateLimit`), `AUTH_KV` as secondaryStorage (sessions live in KV, not D1; no cookieCache), 30-day sessions, `cf-connecting-ip` for IPs, `baseURL.allowedHosts` = production, every `*.patternchess-1et.pages.dev` preview and localhost. Providers: Google (`socialProviders.google`, only when `GOOGLE_CLIENT_ID` + `GOOGLE_CLIENT_SECRET` are set; redirect URI `/api/auth/callback/google`), Lichess (`genericOAuth`, public PKCE client `patternchess`, user info from `lichess.org/api/account`; `account.accountId` = lowercase Lichess id), and email/password **only when `AUTH_TEST_MODE=1`** (preview + local, for tests; never production). Users kept their Supabase uuids (`user.id`). Lichess users have no email, so better-auth stores `<lichessId>@lichess.invalid`; treat it as "no email" everywhere via `isPlaceholderEmail` (`src/lib/authClient.ts` / `functions/_shared/auth.ts`) — `AuthUser.email` is already null for them. A `databaseHooks.user.create.after` hook inserts the default `profiles` row (`createProfileForUser`). Client: `authClient` (`better-auth/react`, `src/lib/authClient.ts`); `authService.signInWithGoogle/Lichess` call `authClient.signIn.social` (genericOAuth providers go through `signIn.social` too). `<AuthProvider>` reads `authClient.useSession()`, maps it to `AuthUser` (`provider: 'google' | 'lichess' | 'email'`, `user_metadata`/`app_metadata` mirrors kept for old readers), caches the id for `currentUserId()` (`src/services/db/currentUser.ts`), scrubs auth params from the URL, then `getOrCreateProfile()` (`profile.getOrCreate`) and `claimReferral`. A session that outlived its `user` row (deleted from D1 while the KV session stayed valid, e.g. a test-account cleanup) gets `no_user` from `profile.getOrCreate`; `AuthProvider` signs it out (`endOrphanSession`, which re-reads the session first so a newer sign-in is never revoked). Server code gets the user with `getSessionUser(request, env)` (cookie); admin = `isAdminEmail` (`ADMIN_EMAILS` in `src/auth/admin.ts`, never a placeholder email).
- **Backend RPC + D1** (2026-11-22): every data call is `rpc<T>(name, args)` (`src/lib/api.ts`; `POST /api/rpc/<name>` → `{ data }` | `{ error: { code, message } }`, throws `ApiError`) from the functions in `src/services/db/*` (signatures unchanged from the Supabase era; components keep importing `supabaseService`). Server: `functions/api/rpc/[name].ts` → registry in `functions/_shared/rpc/index.ts` (`DOMAINS`: meta, leaderboard, admin, openings, training, profile; a duplicate name throws at startup). Handlers are named `<domain>.<function>` and wrapped in `userRpc` / `adminRpc` / `publicRpc` from `./core` (never import `./index` from a domain module). **Authorization lives in code (no RLS):** scope every query by `ctx.user.id` and never take a user id from args; public handlers are explicit (`landing.stats`, `leaderboard.public`, `funnel.track`, `health`). Use the `functions/_shared/db.ts` helpers (`all/first/scalar/run/batch`, `insertStmt`/`insertManyStmts` with `onConflict`, `updateStmt`, `chunk`, `nowIso`, `uuid`); pass the table name so rows come back through `decodeRow` in the PostgREST shape the client mappers expect (snake_case, real booleans, parsed JSON). D1 rules: ≤100 bound parameters per statement (helpers chunk), multi-statement writes go in one `batch`, timestamps are ISO UTC with ms strings (`nowIso()`), ids are generated in TS (`uuid()`), booleans are 0/1 and JSON/arrays are TEXT — `encodeRow` handles all of it. Errors: `badRequest`/`notFound`/`forbidden`/`conflict` → 4xx; anything else is a logged 500 with the message hidden. Handler tests run on the real schema with `openTestD1()` (`functions/_shared/rpc/testD1.ts`, `node:sqlite`).
- **Stockfish**: never instantiate the worker directly; call `getStockfish()` (lazy singleton) from `src/hooks/useStockfish.ts`. The client tries the multi-threaded lite engine first, falls back to single-threaded.
- **Engine signals**: `evaluatePositionFull(fen, depth=12)` for batch analysis, `evaluateSmart(fen, { movetimeMs, maxDepth, decidedCp?, decidedMinDepth? })` for "smart depth" evals (`go depth N movetime M` — whichever comes first — plus an early `stop` once a decided score lands; used by endgame play-outs and background deepening), `evaluatePositionTimed(fen, movetimeMs, pvMoves)` for plain fixed-time evals (`bestMoveTimed` delegates to it), and `analyzeGame(positions, …)` for game-wide blunder detection. `stop()` aborts only the active search (queue-safe); `stopOpponentSearch()` in `useStockfish.ts` does it for the opponent singleton. The training screen's on-the-fly accept rule is `evaluatePositionFull(fen, 18)` in `trainingStore`. Every `PositionEval` carries the achieved `depth` (parsed from the last scored info line).
- **Blunder detection** uses the Lichess winning-chances model in `src/chess/winningChances.ts`. Trainable threshold: ≥15% chances lost. On-the-fly accept rule for the training screen: |chancesLost| ≤ 5%.
- **Opening classification** (2026-09-16): a game's opening comes from the board, never from PGN headers — lichess sends `[Opening …]`, chess.com sends only `[ECOUrl …]`, and the two sites assign different ECO codes to the same game. `src/chess/openingClassifier.ts` replays the moves and keeps the **deepest** matching position in `src/generated/openingBook.json` (EPD → `"<eco>|<name>"`, built by `scripts/build-opening-book.mjs` from the CC0 lichess-org/chess-openings TSVs), so transpositions land on the same opening. It writes `games.opening_family` (the grouping key, e.g. "Sicilian Defense") plus canonical `eco`/`opening_name`. Games under `MIN_CLASSIFY_PLIES = 4` (aborts) and non-standard variants (Chess960, Crazyhouse — chess.js can't replay them) stay NULL and drop out of opening stats, which is correct. New games classify at insert via `classifyGameRowsForInsert` (sync + PGN upload); legacy rows are picked up by `startOpeningBackfill` on the dashboard, gated by `opening_classified_at` (stamped even when unclassifiable, so rows are never retried forever). **Never group openings by ECO family again** — `B33`→`B3*` split one opening across up to eight rows and gave unrelated families the same label (the Sicilian spanned eight). The book is a lazy `import()` (~429 KB, 68 KB gzipped); never import the JSON from app code.
- **Spaced repetition**: `SPACED_REPETITION_DAYS = [1, 3, 7, 21]` + `MASTERED_REVIEW_DAYS = 56` (`src/models/blunder.ts`; shortened from a 7-rung/112-day ladder on 2026-09-02 — intervals must stay *expanding*). Index 0 is the new/just-failed interval; `intervalDaysForCycle()` walks the rungs and holds at the 56-day maintenance interval once mastered (mastered positions never leave the queue). Each successful first-attempt drill advances `cycleNumber` by 1; a first-attempt fail resets it to 0 and sets `lastDrillFailed = true`. Retries within the same session don't move the SR state — only the first attempt counts. The canonical implementation is `applyDrillResult` in `src/state/drills/applyDrillResult.ts` — never reimplement the ladder inline.
- **Trainable-item kinds**: `blunders.kind` ∈ `tactic | endgame | opening` (dedup key `(user_id, fen, kind)`; per-kind payload in `drill_data`; `game_id` nullable). The due queue (`getDueBlunders`) is deliberately **unfiltered** — all kinds interleave at `/training`, and tactic/endgame items conceal their kind until the user's first move (that's the product: in a real game you don't know what type of position you're in). **Opening items are the exception** (2026-10-02): they start in trainingStore phase `introducing`, replaying the user's own game up to the position (`introLineTo` in `src/chess/openingLine.ts`, 400 ms/ply, skippable with the button or Space; first showing per session only), then prompt "Play the move for White/Black". `/training` also accepts `location.state.kindFilter` ("Review N due" per kind) and `blunderIds` + `focusLabel` (drill specific positions, due or not, via `getBlundersByIds`). The focus shape is `TrainingFocus` (`src/routes/training/trainingFocus.ts`, 2026-11-22): **a focus is sticky** — "Keep training" continues it via `continueFocus` (an openings session, or a `blunderIds` set of opening drills, continues as `kindFilter: 'opening'`; never the main queue), and `returnTo` (`/openings` | `/endgames`, inferred by `returnPathFor`) adds "Back to Openings/Endgames" to the banner, the complete screen and the empty state. The landing has Openings (`kindFilter: 'opening'`) and Endgames (`phaseFilter: 'endgame'`) focus tiles: "N due", else "Practice ahead" when `blunders.upcoming` has something for that focus, else "None yet", which leads to `/openings` / `/endgames` (never offer practice ahead on a focus with no positions; an empty practice-ahead queue means the focus has none, so its copy is `train.empty.nothingYet`). Restarts remount `TrainingSession` after `flushTrainingWrites()` so the next queue is never the pre-session list. **Practice ahead** (`practiceAhead: true`): the user-scoped RPC `blunders.upcoming({ kind?, excludeKind?, phase?, limit })` (live, not yet due, soonest first; `useUpcomingBlunders`, `practiceAheadParams`, batches of 10, openings excluded unless the focus is openings) feeds the same drill loop, so results go through `applyDrillResult` unchanged. Every empty state (training, plan) offers it — never write "see you tomorrow"/"come back tomorrow" dead ends. Game-analysis aggregates (phase/motif/per-game counts, vault, insights) filter `kind = 'tactic'` (in the RPC handlers' SQL); SR-ladder aggregates (cycle distribution, blunder stats, due counts) stay unified. In `/training`, tactic items use the stored-sequence drill in `trainingStore.processMove`; endgame items render `EndgameDrillView`, which drives its own play-out store and reports the outcome via `trainingStore.completeExternalDrill`; opening items reuse the tactic path as single-move drills (`solution_line` NULL, `correct_moves` = the masters theory moves); a correct answer sets `trainingStore.openingVerdict` (`repertoire` | `book` | `sound` — "Great!" / "Good move") rendered by `OpeningVerdictPanel` with **Add to repertoire**, and a miss retries in place (not requeued). Labels come only from `DRILL_KIND_LABEL`. `deleteBlundersForGame` (Vault re-analyze) skips `kind='opening'` — those rows are deduped across games that share one `game_id`.
- **Endgame trainer** (`/endgames`): `endgameScenarioService` crosses existing endgame-phase blunders with `resolveOutcome` (dropped win: `missedWin` + loss/draw; dropped draw: `roughlyEqual` + loss), one scenario per game in `endgame_scenarios`. Play-outs run vs the opponent engine at full strength, adjudicated by `src/chess/adjudication.ts` (terminal states via chess.js FIRST — `parseEvalCp` returns an ambiguous 0 there; giving up the target result → fail + slip optionally logged as an endgame-kind item). Two rule sets: `HOLD_RULES` for queue drills (hold the deserved eval for `HOLD_MOVES = 10` user moves → success) and `FINISH_RULES` for `/endgames` (win = checkmate only, any draw condition fails it; draw = draw by rule or `engineAcceptsDraw` — dead-level at depth with no pawn move/capture for 16 plies, or textbook pawnless material). The store (`endgamePlayoutStore`) keeps the board live while the reference eval runs in the background (`refPending`), commits the engine reply before the next eval, tracks repetition itself, and offers `takeBack()` only when started with `allowTakeBack` (Endgames tab; free). **Endgame engine budgets are time-capped** (2026-10-27): ref/hint 5s, judge 3s, confirm 6s, all `maxDepth: 50` as a backstop and **no `decidedCp` early stop** (a shallow +10 cutoff made the deeper post-move search fail the engine's own hinted move — the horizon effect). Every would-be slip gets a second look (`confirming`, "Double-checking…") via `confirmSlip`: the hinted move or the deeper best move is never a slip, nor is any move within 5% of best. `parseEvalCp` prefers exact scores over `lowerbound`/`upperbound` lines. **Endgame scenarios are on the SR ladder** (2026-10-02): `cycle_number`/`times_*`/`last_drill_failed`/`last_drilled_at`/`next_drill_at` on `endgame_scenarios`, advanced only via `applyScenarioResult` (shares the pure `advanceSr` with `applyDrillResult` — never reimplement the ladder); the first finished play-out per visit is the first attempt, and a pass stays `status='passed'` (rescue achievement). `/endgames` has "Review N due" (a run through due scenarios with "Next due"), `MasteryDots` + `SR_BUCKET_LABEL` per card, Due/bucket filters, and an endgame-type filter (`?type=`, also narrows "Review N due"); sections show 24 cards then "Show more". `/endgames` groups scenarios by `classifyEndgameType` (`src/chess/endgameType.ts`; `ENDGAME_TYPE_LABEL` is the only label source).
- **Endgame scenario verification** (2026-09-15): scenarios are still derived engine-free from the depth-12 eval, but `startEndgameScenarioVerification` (`src/services/endgameScenarioVerifier.ts`, mounted on the dashboard and `/endgames`) re-evaluates each new row's `start_fen` with a 5s time-capped search (depth-50 backstop, no decided stop; existing rows were re-queued on 2026-10-27) and stamps `verified_at` / `verify_eval_cp`; `verdictFor` retires (`retired_at`) dropped draws outside ±150cp or below `DRAW_HOLD_PCT`, and dropped wins under +300cp (already-`passed` rows are never retired). `getEndgameScenarios` and `getEndgameCandidateBlunders` (`endgameScenarios.list` / `blunders.endgameCandidates`) filter `retired_at IS NULL`. It yields to sync analysis and `isMaintenanceRunning()` (same analysis engine).
- **Drill feedback prefs** (2026-09-25): two post-miss settings apply to every drill surface — `showAnswer` (`profiles.show_answer_on_miss`, default off: green best-move arrow + a stepable Solution line) and `autoplay` (`profiles.autoplay_refutation`, default on: after **every** miss, first attempt included, play the refutation of the played move, then the solution when `showAnswer` is on). Read/write them only via `useDrillFeedbackPrefs` (`src/hooks/`; optimistic, shared across mounts) and run autoplay only via `useLineAutoplay` (segments stepped at 700 ms, `stop`/`skip`, `active` for overlays). Toggled from the gear (`DrillSettingsMenu`, rendered by `BoardActionBar`, so any drill using the action bar gets it) and `/profile`. Tactics: `trainingStore.solutionMoves` + `selectSolutionIndex(-1 = arrow)`; endgames: `useSlipLineViewer` builds the solution from `slip.refEvalAtSlip` PV and applies both prefs itself. The "good but not best" retry-in-place never reveals the answer.
- **Repertoire** (2026-10-02): `repertoire_moves` (D1; one move per `(user_id, color, epd)`, book EPD). `src/services/db/repertoire.ts` (RPCs `repertoire.list` / `repertoire.upsert` / `repertoire.delete` in `functions/_shared/rpc/openings.ts`) + `useRepertoire`/`useAddToRepertoire`; `TrainingRoute` mirrors it into the store. In an opening drill your saved move is always correct and any other good move is a no-SR "Good move, but your repertoire move is X" nudge. `/openings` cards show "Your repertoire" when it differs from what you played; `findRepertoireExit` (`src/chess/openingLine.ts`) is the helper for flagging games that leave it.
- **Opponent engine**: `getOpponentStockfish()` is the ONLY client that may ever receive `setoption` (Skill/Elo). Endgame play-outs use it and re-pin `UCI_LimitStrength: 'false'` (`ucinewgame` does not clear option state). Never send `setoption` to `getStockfish()`/`getAnalysisStockfish()`.
- **SR taxonomy** (4 buckets): `new` (never drilled) · `learning` (in the 4-cycle ladder) · `tryAgain` (last drill's first attempt failed) · `mastered` (cycle ≥ `SPACED_REPETITION_DAYS.length`, i.e. 4). Single source of truth: `srBucket()` + `SR_BUCKET_LABEL` in `src/models/blunder.ts`. **Never invent ad-hoc labels** in UI components — always import these. Note: `srBucket(...) === 'mastered'` is just cycle ≥ ladder length; `isMastered()` adds a recall ≥ 80% check and is used only for the global stats achievement count in `getBlunderStats()`.
- **Background deepening**: initial sync analysis stays a fast depth-12 pass (onboarding critical path — never make it deeper/slower). `startBlunderMaintenance` (`src/services/blunderEnrichmentBackfill.ts`) runs only while the dashboard is mounted: it enriches legacy rows, then re-analyzes every row (`kind` tactic|endgame) with a 3s-per-position timed budget (endgame-kind/phase rows: 5s, depth-50 backstop, no decided stop), rewriting evals/`correct_moves[0]`/`solution_line`/motifs and stamping `analysis_depth` (metadata) + `deepened_at` (the completion gate — time-based, NOT a target depth). Rows the deeper pass scores at <10% chances lost get `retired_at` and drop out of `getDueBlunders` (kept in Vault/stats). It never touches `games.analyzed_at`, and exits while unanalyzed games exist so sync analysis keeps the engine.
- **Public-page performance** (2026-09-02): fonts are self-hosted (`public/fonts/*.woff2` via `scripts/sync-fonts.mjs`, `@font-face` + metric-matched fallbacks in `src/styles/fonts.css`, two preloads in `index.html`) — never re-add the Google Fonts stylesheet. Chessground and its CSS load only with the lazy board chunk (`src/chess/LazyChessgroundReact.tsx` for the landing page; `src/styles/chessground.css` is imported by `chessgroundReact.tsx`, not `index.css`). The landing social-proof card renders from `src/generated/landingStats.json` (refreshed by `scripts/fetch-landing-stats.mjs` in `build`) so it is in the prerendered HTML and never shifts layout. `public/_headers` sets immutable caching for `/assets`, `/fonts`, `/stockfish`. Local Cloudflare preview: `npx wrangler pages dev dist --compatibility-date=2026-11-01` (wrangler 4.158; wrangler reads `CLOUDFLARE_ACCOUNT_ID` from `.env.local` and authenticates with the OAuth login).
- **Sounds** (`src/lib/sounds.ts`): everything is synthesized with the Web Audio API — no audio assets (the Lichess sound sets are AGPL; don't vendor them). `BoardPanel` plays move/capture/check off `fen` changes that carry a `lastMove` (pass `sounds={false}` for static preview boards); `TrainingRoute`/`EndgamesRoute` play correct/incorrect on phase changes; `useAchievements` chimes for newly earned ids (seen-set in localStorage). `profiles.sounds_enabled` ("Play sounds" in `/profile`) gates it via `setSoundsEnabled` in `AppShell`; `installSoundUnlock()` resumes the context on the first gesture.

Chess notation (SAN), opening names, player names and "Elo" stay as is; chess terms use the standard local ones (es "error grave / ataque doble / clavada", pt "erro grave / garfo / cravada"). Language: `localeStore` (Zustand) — no stored choice follows `navigator.languages`, a pick is per device in localStorage `pc:locale` (no profile column); `initLocale()` in `main.tsx` loads a non-English catalog before the first render (1.5 s cap) and sets `<html lang>`. Pickers: `LanguageSetting` on `/profile#language` and a select in `LandingFooter` for signed-out visitors (names via `LOCALE_NATIVE_NAME`). Prerendered public pages stay English: `scripts/prerender.mjs` and Playwright both pin `locale: 'en-US'` (specs opt in with `test.use({ locale })`, see `i18n.spec.ts`). Not translated yet: achievements/flair/leaderboards/path/courses/learn/events/supporter pages, Worker emails, share images, testimonials (verbatim quotes) and the `WhyYouAreStuck` footnotes.
- **No emojis in UI**: never render Unicode emoji (fire, checkmarks, etc.) in components. Use inline SVG icons — follow the `BrandMark` pattern in `src/components/BrandLogo.tsx` for hand-written SVGs, or add new ones under `src/components/icons/` (see `FlameIcon` for the established shape: palette constants, `viewBox="0 0 24 24"`, `aria-hidden` by default with optional `title`).

### Verifying UI changes

After any UI / behavior change, **start the dev server and exercise the affected
screens with the Playwright MCP** (`mcp__playwright__*` tools) before reporting
the task as done. `npm run typecheck` and the Playwright spec suite verify code
correctness, not feature correctness — they don't catch runtime errors that only
surface at the rendering layer (e.g. chess.js throws on an invalid move,
infinite loading from an unhandled promise, a hidden empty state).

A typical loop:
1. Start `npm run dev` (background).
2. `mcp__playwright__browser_navigate` to `http://localhost:5173`, sign in (or use a stubbed session).
3. Walk through the changed flow and check `mcp__playwright__browser_console_messages` for errors.
4. Take a `mcp__playwright__browser_snapshot` if the visual state matters.

If it can't be tested in a browser, say so explicitly rather than claiming success.

### Sync invariants

- **Already-synced games are not re-fetched.** `syncProvider` dedupes against
  `getExistingExternalGameIds(platform)` (the site's game id, unique per
  `(user_id, platform, external_game_id)`). Lichess game ids come from the PGN
  `Site` header via `extractLichessGameId`, which must accept both
  `lichess.org/<id>` and `lichess.org/game/<id>` (Lichess switched on
  2026-10-22; the old regex silently skipped every game for a week). If every
  fetched game fails to parse, `fetchLichessGames` throws so the indicator shows
  "Sync failed", never "Up to date".
- **PGN uploads of the user's own games use the source id.** When the entered
  name matches a player and `Site`/`Link` names a Lichess or chess.com game,
  `pgnUploadService` stores it as that platform + game id (`pgnSourceGame`), so
  a later sync (or a re-export with different headers) dedupes against it.
  Everything else stays `platform='pgn'` keyed by a SHA-256 of the text.
  Older uploads were converted and merged on 2026-10-28.
- **Leftover games get analyzed on the dashboard.** Sync only analyzes its own
  platform + username, so `startBlunderMaintenance` first finishes any
  `analyzed_at IS NULL` game (`getLeftoverUnanalyzedGameIds`, all platforms),
  yielding to an in-flight sync (`isAnySyncInFlight`). `analyzeGames` stamps a
  game that fails to analyze instead of aborting the batch.
  `countUnanalyzedGames` (every background job's "sync busy?" gate) remembers a
  **zero** for 30s; `insertGames` and `resetGameAnalyzed` forget it. Never
  cache a nonzero count — waiting jobs must see it drop. Maintenance refreshes
  the motif card at most every 2 min (`MOTIF_REFRESH_MS`) plus once at the end.
- **Bulk delete** (`BulkDeleteGamesModal`, Vault Games tab): played-before-date
  or all, via `deleteGames(ids)` (`games.deleteMany`) in 100-id chunks; D1
  enforces the FKs, so blunders/annotations/scenarios/deviations cascade.
- **Already-analyzed games are not re-analyzed by sync.** `getUnanalyzedGameIds`
  filters `analyzed_at IS NULL`. Only the per-game "Re-analyze" button in
  `/vault` (which explicitly resets `analyzed_at` and deletes existing blunders)
  can re-analyze a game.

## Database migrations (D1)

The app database is D1 `patternchess-app` (`7d359ac5-7829-4a4d-8fa9-5af6379cdf15`; preview and production share it, so a remote migration changes production data at once — keep them additive, and remove test accounts made on a preview). To change the schema:

1. Add `d1/migrations/000N_<name>.sql` (SQLite; next free number — never edit an applied file). Follow the type mapping in `d1/README.md`: uuid/timestamps/JSON/arrays → `TEXT` (ISO UTC with ms; `json_valid` CHECK on JSON), booleans → `INTEGER` 0/1 with an `IN (0, 1)` CHECK, FKs to better-auth's `user(id)`.
2. Register new tables and every new boolean / JSON / timestamp column in `TABLES` in `functions/_shared/schema.ts` (that is what turns rows back into the PostgREST shape) and update `functions/_shared/schema.test.ts`.
3. Apply locally: `npx wrangler d1 migrations apply patternchess-app --local --config d1/wrangler.jsonc --persist-to .wrangler/state` (or just restart `scripts/dev-api.sh`). Handler tests pick it up automatically (`openTestD1()` applies every file in `d1/migrations`).
4. Apply remotely — this changes the shared preview database, so do it when the branch is ready: `npx wrangler d1 migrations apply patternchess-app --remote --config d1/wrangler.jsonc` (set `CLOUDFLARE_ACCOUNT_ID` from `.env.local` and unset its stale `CLOUDFLARE_API_TOKEN` first).
5. Run `npx vitest run` and `npm run typecheck:functions`; if the notifier reads the table, `npm run typecheck:notifier` and its `store.test.ts`.

`supabase/migrations/` is **historical**: it documents the Postgres schema the D1 one was ported from (2026-11-22) and is never applied again. Production has run on Cloudflare from `main` since the cutover (`docs/cutover-cloudflare.md`, 2026-11-22); after two quiet weeks (from 2026-12-06) the runbook pauses the Supabase project and deletes `supabase/`.

## Production hosting

Whichever host you pick must send these headers:

```
Cross-Origin-Embedder-Policy: require-corp
Cross-Origin-Opener-Policy: same-origin
```

Otherwise Stockfish drops to single-threaded only. The Cloudflare Pages project `patternchess` sends them via `public/_headers`; it also needs the `nodejs_compat` flag and the bindings `DB`, `AUTH_KV`, `CONTENT`, `BOOK` in each environment, plus the secrets listed in `docs/cutover-cloudflare.md` (never `AUTH_TEST_MODE` on production).
